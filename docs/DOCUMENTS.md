# Background draft lifecycle

A POST to the shipment’s `document-jobs` collection accepts a shipment version, document type and UUID idempotency key. Authorization requires both shipment read and document download, including for external collaborators. A transaction saves the exact shipment, resolved settings, settings revision, rendered HTML and HTML hash, then adds a small outbox row. The response is 202 with a durable request ID, even when Redis is unavailable. Reusing the same requester/key returns the original request; changing type, shipment or version with that key returns 409. Pending requests are bounded per requester.

The separate `npm run worker` process dispatches outbox IDs and requester IDs to BullMQ. Redis contains no shipment or document content. Postgres remains the source of truth. Workers claim a row with a fencing token and deadline, check current permissions, render with blocked external network requests and JavaScript disabled, and save the PDF to the configured private storage. The file manifest, SHA-256 and ready state commit together in Postgres after storage succeeds. A stale worker cannot finalize a newer claim. An expired lease can be reclaimed; duplicate delivery of a finished request has no effect. Render failures retry at most three times with backoff; a fresh request is needed after terminal failure. Revocation during rendering prevents file insertion. No successful file is overwritten.

History exposes the latest 50 request summaries for a shipment. Download routes check the current session and permissions, tenant and shipment binding, ready state and saved byte hash. URLs are session-protected API routes, not public object links. Older files remain unchanged after edits. Request/ready/failure/download events are audited. The database runtime role cannot alter snapshots or update/delete saved files. Outbox metadata is internal operational state, has no document contents and is never returned by an API.

PDF files are limited to 10 MiB each. New local files use private S3-compatible storage after setup; existing Postgres files remain readable without being rewritten. Production S3 uses workload IAM credentials, HTTPS, encryption and private bucket policy. Retention, total storage quotas and orphan reconciliation remain release work. A draft request is not a numbered issued document. The synchronous PDF endpoint remains for compatibility; the web app uses background jobs. Production must run and monitor the separate worker, configure Redis TLS/authentication/persistence/no-eviction and database backups, and track outbox age and terminal failures. Production deployment is not completed by this local change.

Integration coverage uses a disposable database and a uniquely named queue. It proves idempotency, optimistic versions, immutable snapshots and files, access boundaries, renderer failure exhaustion, expired-lease recovery, duplicate delivery, revocation during rendering, actual Redis/BullMQ processing and the browser download/history flow.

## Private storage rollout

Run `npm run db:migrate` first, then deploy the compatible API reader everywhere while workers still write Postgres files. Configure the private bucket and deploy the worker with `DOCUMENT_STORAGE=s3`. Rollback the write mode to `postgres` using this compatible release if needed; keep the S3 endpoint, region and workload permissions so existing object-backed files still download. Do not roll back to binaries predating migration 004 once object-backed files exist. No contract migration or deletion of old bytea files is performed.

For local development run `npm run storage:setup-local`, which generates credentials without changing existing secrets, starts the pinned loopback-only SeaweedFS container and verifies that anonymous bucket access is denied before switching new writes to S3. Restart API and worker after environment changes. Only port 8333 is exposed, on loopback. The local seeded storage identity is a development administrator; use separate restricted workload roles in production. The service’s data volume is retained across ordinary restarts.

For AWS, `infra/aws/document-storage.yaml` provides an undeployed CloudFormation template with a retained, private, versioned, encrypted bucket, TLS and conditional-write enforcement, plus separate read and worker IAM policies. Choose the bucket name and attach those policies to workload roles. The API needs only GetObject/GetObjectVersion. Workers also need conditional PutObject. Runtime roles have no DeleteObject or bucket-wide listing permission. AWS uses the default credential chain, so EC2 instance roles can supply credentials without static keys. Never deploy the local development key to AWS.

Objects use server-generated tenant/job/fenced-attempt keys. PUT uses `If-None-Match: *`; an ambiguous retry reuses a key only after verifying the stored byte count and SHA-256. Exact object version IDs are retained when the provider supplies them. Downloads buffer at most one 10 MiB PDF, verify its hash, then recheck the session and permissions before sending bytes. No raw or presigned object URLs are returned to the browser.

S3 and Postgres cannot commit atomically. An upload followed by a failed or uncertain database commit can leave a private orphan. Each attempt uses a distinct key; the app never deletes an uncertain object or overwrites a committed file. Orphan inventory/reconciliation must compare against retained manifests after a grace period; do not expire the entire drafts prefix or delete objects during a transient DB failure. Bucket backup/version retention and restore testing are separate from database backups. Keep both until a verified retention and reconciliation process is in place.

Additional integration checks exercise actual local S3 writes, private anonymous denial, conditional overwrite rejection, concurrent upload retry, corrupted bytes, failed writes, legacy reader compatibility, and membership/session revocation while an object is being retrieved. Test cleanup removes only its randomly generated tenant prefix, never existing app objects.
